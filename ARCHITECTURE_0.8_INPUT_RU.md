# AgentBridge 0.7 — архитектура универсального Android-агента

**Дата:** 19 октября 2026 г.  
**Статус:** предлагаемая рабочая концепция для обсуждения и последующей сборки; документ не подтверждает наличие готового APK.  
**Исходная база:** `AgentBridge-0.6.0-multiprovider-voice-source.zip` (основана на 0.5.5).

## 0. Цель и принципы

AgentBridge — единый Android-агент для управления устройством через инструменты Bridge. Он умеет общаться текстом и голосом, использует сменяемые LLM (Gemini, OpenAI, Anthropic Claude, OpenAI-совместимые локальные или удалённые API), **обладает собственной долговременной общей памятью**, постепенно учится проверенным сценариям и не требует повторяющихся объяснений.

1. **Агент принадлежит приложению, а не провайдеру.** Память, задачи, журнал, каталог инструментов и правила безопасности независимы от LLM.
2. **Сначала результат и его проверка, затем скорость.** Ответ модели не является доказательством выполнения действия. Инструменты подтверждают операцию, затем агент проверяет конечное состояние.
3. **Минимальная рутина.** Обычная навигация выполняется без подтверждения каждого нажатия. Проверка опасных операций проводится на уровне контроллера, независимо от модели.
4. **Память — не огромный промпт.** Факты сохраняются локально; в контекст каждой операции выбирается полезный небольшой фрагмент.
5. **Один голосовой/текстовый диалог.** Речь распознаётся в текст; выход модели преобразуется в речь независимо от выбранной LLM.
6. **Прозрачность.** Видно, какая модель используется, что агент собирается сделать, что он действительно сделал и почему остановился.
7. **Переносимость.** Состояние и знания экспортируются в открытом формате; можно перенести в другой чат, на другую сборку и в будущем синхронизировать.

## 1. Что реально есть в исходниках 0.6.0

- `AgentContext.kt`: общие редактируемые заметки до 6000 символов, стартовые сведения об устройстве; отправка их в системный контекст.
- `DialogueMemory.kt`: 4 пары «задание—ответ» только в RAM, исчезают после завершения процесса.
- `AgentPrefs.kt`: конфигурации Gemini, OpenAI, Anthropic, совместимого API; ключи хранятся отдельно с использованием Android Keystore; знания пока в SharedPreferences.
- `ProviderEngine.kt`: адаптеры форматов LLM, общий набор tool calls.
- `PanelActivity.kt`: один длинный экран со всеми настройками и заданиями; голос по нажатию кнопки через системный RecognizerIntent; озвучивание итогов через Android TTS.
- `AgentRuntime.kt`: выполнение задач, правила навигации и остановки; пока нет постоянных checkpoint в базе.
- `AgentApproval.kt`: эвристическое выявление некоторых опасных нажатий по строке элемента; **не является полной защитой**.
- `AgentService.kt`: фоновое выполнение с уведомлением и кнопкой остановки.
- **Проверки:** 0.6.0 не проходила полноценную Android-сборку/испытание на телефоне; исходники нельзя считать доказательством работоспособности.

## 2. Архитектура: пять независимых слоёв

```text
┌──────────────────────────────────────────────────┐
│ UI: Агент | Память | Настройки | Журнал           │
│     текст / кнопка микрофона / озвучивание        │
└──────────────────────┬───────────────────────────┘
                       │
┌──────────────────────▼───────────────────────────┐
│ Agent Controller                                 │
│ Task State Machine | План | Проверка результата  │
│ Risk Gate | Retry / Quota | Stop / Recovery       │
└───────────┬─────────────────────────┬────────────┘
            │                         │
┌───────────▼────────────┐ ┌──────────▼────────────┐
│ Memory / Context       │ │ Provider Adapters      │
│ Core facts             │ │ Gemini | OpenAI        │
│ App facts, procedures  │ │ Claude | Compatible    │
│ Task checkpoints       │ │ future / local         │
│ Search / Retrieval     │ └───────────────────────┘
│ Import / Export        │
└───────────┬────────────┘
            │
┌───────────▼──────────────────────────────────────┐
│ Tool Gateway: Accessibility / Browser / MCP       │
│ Снимок UI → Действие → Новый снимок → Сравнение │
│ Разрешения/ограничения проверяются здесь          │
└──────────────────────────────────────────────────┘
```

API провайдера — **адаптер обмена сообщениями и tool calls**, а не хранитель знаний и не исполнитель Android-команд напрямую. Аудиоввод/вывод — отдельные заменяемые адаптеры `SpeechToText` и `TextToSpeech`.

## 3. Интерфейс: стандартизация

### 3.1. Нижние вкладки (4)

**Агент** — главный экран. Чат и история беседы, кнопка 🎤, ввод текста, индикатор активной модели, индикатор Bridge/Accessibility, текущий этап задачи, `Стоп`, сворачиваемое «Что делал агент», возможность продолжить прерванное задание. Не смешивать с ключами API.

**Память** — поиск, категории знаний, просмотр источника и даты проверки, закрепление, ручное исправление, удаление, очередь предложений к запоминанию, импорт/экспорт, кнопка «Чему ты научился?».

**Настройки** — вложенные разделы: `Модели` (профили и провайдеры), `Голос` (распознавание/озвучивание), `Bridge` (доступность, инструменты, разрешения), `Безопасность` (политики, обмен данными, чувствительные данные), `Дополнительно` (лимиты задач, диагностика, резервное копирование).

**Журнал** — понятная хронология: «запланировано → вызван инструмент → получен результат → подтверждено», фильтры по задачам и ошибкам, экспорт обезличенной диагностики. Журнал не обязан хранить сырые снимки экрана.

### 3.2. Правила UI

- Одинаковые компоненты настроек для всех провайдеров: `провайдер`, `модель`, `ключ`, `конечная точка`, `проверка подключения`, `применить`.
- Отображать активного провайдера в заголовке агента; смена для **следующего шага/задания** не должна скрытно прерывать текущее действие.
- Ключ никогда не показывать открытым по умолчанию, не копировать в журнал; скрывать в экспортируемом файле.
- Главный экран — без длинной прокрутки настроек. Поддержать тёмную тему, крупные кнопки, доступность шрифтов/скринридера.
- `Стоп` всегда доступен во время работы; при проблеме показывать конкретный тип: 429, отказ доступа, не найден элемент, блокировка экрана, ожидание пользователя.

## 4. Общая память: шесть категорий

1. **Базовый контекст (Core).** Проверенные факты: конкретное устройство, прошивка, возможности Bridge, предпочтения владельца по управлению. Версионированный и закрепляемый. Не переписывать автоматически на основании единичного ответа LLM.
2. **Карта приложений (Apps).** Название, фактически наблюдённый package name, известные разделы/экраны, особенности навигации, последние проверки. Учитывать изменения версии приложения; resource ID и координаты не являются вечными.
3. **Рецепты (Procedures).** Успешные сценарии: предварительные условия, последовательность **логических** действий (не жёсткие координаты), критерии успеха, дата/версия, возможные ошибки и методы восстановления.
4. **Эпизоды (Episodes).** Краткие итоги завершённых задач и проверенные результаты, без необходимости хранить всю переписку/экран.
5. **Задачи и контрольные точки (Tasks).** Цель, план, текущий этап, выполненные и проверенные шаги, ожидаемый эффект, активное приложение, использованная модель, точка безопасного продолжения. Сохранять между перезапусками.
6. **Импортированные знания (Library).** .md/.txt/.json и в будущем данные пользователя из разрешённых хранилищ. Не смешивать доверенные правила агента с внешними документами или экранным текстом.

**Критично:** «все знания» означает **вся сохранённая база доступна поиску всеми моделями**, а не отправку всей базы каждому провайдеру при каждом обращении.

### 4.1. Модель записи (пример)

```json
{
  "id": "uuid",
  "kind": "app_fact|procedure|core|episode|task|library",
  "scope": "global|device:<id>|app:<package>|project:<id>",
  "title": "Проверенный сценарий запуска",
  "content": "...",
  "source": "owner|verified_tool_result|imported_file|model_proposal",
  "verification": "confirmed|pending|stale|rejected",
  "confidence": 0.95,
  "created_at": "ISO-8601",
  "verified_at": "ISO-8601-or-null",
  "expires_at": null,
  "sensitivity": "normal|private|secret",
  "tags": ["navigation", "app"],
  "revision": 1
}
```

Содержимое записи *является данными*, а не новым системным приказом. Приоритет правил: правила безопасности и разрешений владельца > текущая просьба владельца > закреплённый контекст > извлечённые факты > внешнее содержимое.

### 4.2. Хранилище и поиск

- Перейти от одного поля в SharedPreferences к локальной структурированной БД: SQLite через Room (или эквивалентный Android SQLite API).
- Поиск по ключевым словам, категориям, приложению и проверенности (FTS4 с Unicode tokenizer при доступности). **Эмбеддинги/векторную БД на первой итерации не требовать**.
- Контекст каждого запроса собирать из системной политики, небольшого блока Core, текущей задачи, свежих проверенных фактов по активному приложению, релевантных рецептов и последних реплик диалога.
- Разрешить владельцу закреплять записи для постоянной выдачи и запрещать включать отдельные записи в контекст облачных моделей.
- Обеспечить миграцию 0.6: `ownerNotes` → Core/Library, модельные ключи остаются в старом защищённом хранилище, история RAM уже недоступна после перезапуска.
- Шифровать приватную БД на устройстве либо не сохранять чувствительные сведения до реализации безопасного хранения. Android Keystore использовать для ключей; учесть root-модель угроз и резервное копирование. Никакие секреты не попадут в plain-text export.

### 4.3. Обучение без «обезьяньей работы»

- Автоматически сохранять технические факты, **подтверждённые инструментами**, например наблюдённое название пакета или успешный проверенный переход; не выдавать гипотезу модели за факт.
- Предлагать извлечённые инструкции/рецепты в очередь; проверенные неопасные можно принимать автоматически по заданной владельцем политике; спорные, личные, чувствительные — только после отдельного разрешения.
- Когда владелец один раз исправил способ действия, фиксировать исправление и применять его как подсказку в будущих аналогичных случаях после проверки совпадений.
- Каждая запись несёт источник, время, версию приложения и уровень достоверности. При расхождении с новым состоянием — пометить устаревшей, а не безусловно повторять старое.
- Ограничивать размер/дублирование: объединять повторные эквивалентные наблюдения и иметь ручной инструмент «очистить устаревшее».
- Показать в UI разницу между «знает», «предполагает» и «проверено сейчас».

## 5. Task State Machine: непрерывность между моделями

Состояния: `IDLE → PLAN → ACT → VERIFY → (NEXT_STEP | COMPLETE)`; ветви `WAIT_USER`, `WAIT_QUOTA`, `PAUSED`, `FAILED`, `CANCELLED`.

- Перед потенциально изменяющим действием сохранять контрольную точку: цель, текущая стадия, ожидаемое изменение.
- После действия сохранять инструментальный результат и *проверяемый признак успеха*, а не только успех HTTP или `tap`.
- При 429 сохранять состояние WAIT_QUOTA; **не воспроизводить уже выполненный Android-клик**, когда лимит откроется. Показать состояние и предложить переключение модели или ручное продолжение.
- При переключении провайдера формировать нейтральную структурированную карточку: задача, достигнуто, осталось, текущее проверенное состояние, ограничения, идентификатор checkpoint. Новому провайдеру не нужен сырой разговорный протокол старой модели.
- При перезапуске приложения показывать «Незавершённая задача» и предоставлять варианты `Продолжить / Просмотреть / Отменить`; перед продолжением обязательно проверить активный экран.
- Не исполнять два независимых агентных потока одновременно в одной Accessibility-сессии; разрешить очередь заданий, но один активный исполнитель.
- Прерывание по кнопке «Стоп» должно прекращать текущую задачу и будущие действия; вызовы стороннего API и Android-инструменты могут не прерываться мгновенно — нужен механизм запрета *следующих* действий после отмены.

## 6. Провайдеры и выбор моделей

Интерфейс адаптера: `generate(system, turns, tools, settings) -> assistant text | tool calls | recoverable error`.

- Gemini / OpenAI Responses / Anthropic Messages / OpenAI-compatible Chat Completions; без обещания, что любой совместимый endpoint поддерживает tool calls.
- Профиль каждого провайдера: ID, endpoint, модель, отдельный ключ, таймаут, ограничение стоимости/шагов, параметры генерации, флаг передачи приватных данных.
- Отдельный экран «Проверить соединение» с безопасным read-only тестом; **не выполнять действия в интерфейсе телефона для проверки ключа**.
- Настройка первичной модели и запасных; **автоматический fallback из облака в облако выключен по умолчанию**, поскольку меняет адресата данных. При включении пользователь выбирает разрешённых получателей.
- Не смешивать стоимость подписок ChatGPT/Claude с API-биллингом; пользователь сам вносит соответствующие API-ключи.
- Не конвертировать сырые внутренние структуры одной модели в якобы универсальную историю без валидатора. Для смены модели использовать краткий нормализованный TaskCheckpoint + релевантную память.

## 7. Голос

### v0.7 — надёжный голосовой диалог

- Кнопка **нажать и говорить** на экране «Агент»; необязательная отдельная кнопка на уведомлении/гарнитуре при доступности платформы.
- Речь → текст (STT) → контроллер → ответ → синтез речи (TTS).
- Показ распознанного текста перед потенциально опасным действием; для обычных задач запуск без обязательного второго подтверждения.
- Настройки: язык `ru-RU`, сервис распознавания, локальное распознавание когда доступно, TTS движок, скорость речи, высота голоса, озвучивать итоги/ошибки, пауза аудио по кнопке Стоп.
- Проверять `SpeechRecognizer.isOnDeviceRecognitionAvailable()`; не обещать offline на конкретной прошивке без теста. Android-документация предупреждает, что обычный SpeechRecognizer может использовать сеть и не рассчитан на непрерывное прослушивание.
- При отсутствии STT сохраняется полноценный текстовый режим. При отсутствии TTS сохраняется текстовый ответ.

### позже, не блокировать v0.7

- Потоковая двусторонняя речь, wake word, работа при заблокированном экране, автономное hands-free; проектировать отдельно с учётом разрешений микрофона, энергопотребления и приватности.

## 8. Безопасность, права, приватность

- Уровни действий: `read` — автоматически; `reversible_navigation` — автоматически; `write` — разрешено только в пределах явной задачи и политики; `high_risk` (платёж, перевод, публикация/отправка важного сообщения, удаление, сброс, установка/передача разрешений) — согласование конечного эффекта. Не требовать подтверждений на каждую обычную навигацию.
- Усилить `AgentApproval`: текущий Regex по тексту целевого узла недостаточен. Решение должно учитывать класс инструмента, намерение пользователя, семантику операции и активное приложение, а не только слова кнопки.
- Хранить параметры разрешения на конкретное действие/цель и исключить повторный обход отказа альтернативными инструментами.
- Внешний текст из браузера, почты, чата и заметок — недоверенные данные; не исполнять вложенные «инструкции для агента».
- Не сохранять автоматически пароли, токены, банковские данные, одноразовые коды, содержимое личных переписок, полные снимки экранов. Выделить режим локальной/облачной обработки и индикатор передачи данных.
- Кнопки `Остановить`, `Очистить историю`, `Удалить память`, `Экспорт без секретов`, `Отключить микрофон`.
- Не обещать абсолютную защищённость Android-устройства с root; считать root расширенной поверхностью риска и минимизировать дополнительные привилегии.

## 9. Импорт/экспорт знаний

- `memory_export.json` — записи с версиями, происхождением, подтверждённостью и scope без секретов.
- `agent_context.md` — компактная человекочитаемая выжимка для других моделей/чатов.
- `task_checkpoint.json` — незавершённая задача для восстановления в другом сеансе.
- Импорт `.md`, `.txt`, `.json` с предпросмотром и назначением категории. Не импортировать внешние инструкции как системные правила без выбора владельца.
- В перспективе — синхронизация с Google Drive/локальным сервером после разрешения пользователя, версионирование и разрешение конфликтов; не обещать, что память ChatGPT/Claude доступна приложению автоматически.

## 10. Границы v0.7.0 (чтобы действительно собрать)

**Обязательно для первого APK:**

1. Четыре вкладки UI + вложенные разделы настроек.
2. Сохранение и миграция провайдерских профилей без потери текущих ключей.
3. Локальная БД базовых знаний, приложений, рецептов, итогов и checkpoint.
4. Сборщик контекста с выборкой, без ограничения «вся память = 6000 символов».
5. Простая проверяемая политика записи памяти и UI исправления/удаления.
6. Текст/пошаговый голос; вывод TTS; ручной выбор провайдера.
7. Журнал и проверка каждого изменяющего действия; восстановление после 429.

## 14. Дополнение 19 октября 2026: очередь API и лимиты

**Статус:** согласованные требования следующей итерации; реализация ещё не подтверждена. Дополнение уточняет разделы 5–7 и входит в обязательный объём следующей сборки.

- Все обращения к LLM, включая диалог, планирование, проверку и повторы, проходят через единый планировщик. Квоты учитываются по провайдеру, проекту/аккаунту и фактической группе квоты модели; разные API-ключи одного проекта не считать независимыми квотами.
- Хранить настраиваемые RPM, входные TPM, RPD (когда применимы), историю отправок, доступное время следующего запроса, blocked_until, число попыток и срок ожидания задачи. Не зашивать неподтверждённые квоты или названия моделей.
- Разнести запросы по времени с небольшим запасом и учитывать скользящее минутное окно. Пример, а не фактическая квота проекта: при 10 RPM исходный интервал около 7 секунд. Учитывать также токены и суточный предел; минутная пауза не устраняет суточное исчерпание.
- При 429 разбирать Retry-After и поддерживаемые адаптером структурированные подсказки о повторе. Серверный срок считать нижней границей ожидания. При отсутствии подсказки использовать ограниченный exponential backoff с jitter. Не создавать бесконечные повторы.
- Блокировку применять ко всем запросам соответствующей группы квоты; не допускать одновременного пробуждения независимых циклов повторов. Отличать исчерпание квоты от временной перегрузки сервера.
- Ответы на уточнения и новые реплики владельца имеют приоритет перед следующим автономным шагом. Предусмотреть настраиваемый резерв квоты для диалога, справедливость очереди и отсутствие бесконечного голодания фоновых задач. Приоритет не обходит общий лимит.
- Во время WAIT_QUOTA можно выполнять только уже разрешённые локальные действия, не требующие нового решения LLM и не противоречащие новым сообщениям владельца. Один исполнитель управляет интерфейсом телефона.
- Независимые вызовы инструментов можно получать одним ответом модели; зависимые действия с UI исполнять последовательно с проверкой состояния. Объединение шагов не должно обходить актуализацию задачи или остановку.
- В UI показывать причину ожидания, оставшееся время и очередь. Не обещать немедленного ответа при исчерпанной облачной квоте.
- Выбор основной/экономичной/резервной модели делать по реальным квотам проекта, задержке и успешности одинаковых задач. Не считать Flash-Lite автоматически обладателем большей квоты. Смена провайдера остаётся в рамках разрешённых профилей и правил раздела 6.

## 15. Дополнение: постоянный разговор и выполнение задач

**Принцип:** пользователь может обсуждать вопрос, поручать действие, отвечать на уточнение и добавлять условия в одном постоянном текстовом/голосовом диалоге. Выполнение привязано к разговору; завершение задачи не завершает разговор.

### Намерения и состояния

- Различать обсуждение, поручение, ответ на уточнение, изменение текущей задачи, отдельную новую задачу, паузу, продолжение и отмену. Не требовать ручного переключателя «чат/действия» для каждой реплики.
- Предложение «может, удалить дубликаты?» само по себе не команда на удаление; «удали эти дубликаты» — поручение в рамках политики разрешений. Уточнять только существенную неоднозначность; не возвращать подтверждения каждого обычного шага.
- Уточнение модели сохранять вместе с question_id, task_id, ожидаемым ответом и причиной блокировки. Переводить зависимую задачу в WAIT_USER. Ответ продолжает ту же задачу, сохраняя проверенные результаты. При нескольких ожидающих вопросах неоднозначный ответ не привязывать молча.
- Реплики хранить с conversation_id, message_id, временем, ролью и при необходимости task_id/reply_to. Задача хранит task_revision, ограничения, checkpoint, текущий этап и ожидаемый вопрос. План и каждый предложенный вызов инструмента связаны с версией задачи, на которой они построены.

### Дополнения во время работы

- Принимать ввод и во время запроса модели, выполнения, WAIT_USER и WAIT_QUOTA. Реплика сразу сохраняется локально; индикатор «принято» не означает, что модель её обработала.
- Добавление условия к текущей задаче атомарно увеличивает task_revision и помечает затронутый план устаревшим. Не создавать новую задачу для каждого дополнения.
- Если ответ API построен на старой версии задачи, не исполнять предложенные действия без проверки новых условий. При необходимости запросить перепланирование по свежему состоянию.
- Перед передачей изменяющего вызова в ToolGateway атомарно проверять отмену, task_revision, разрешения и актуальность UI. Это исключает гонку между проверкой и отправкой команды. Уже начатое действие может завершиться; не обещать его мгновенный откат. Затем проверить результат и учитывать его в новом плане.
- Для коротких реплик подряд предусмотреть настраиваемое окно объединения без бесконечного откладывания отправки. Для голоса использовать завершённую STT-реплику, не исполнять частичные гипотезы распознавания; последующие дополнения принимать отдельно.
- Разговору отдавать приоритет в API-очереди; уже разрешённая независимая работа может продолжаться, если реплика не требует её остановки или пересмотра. Уточнение о способе работы должно получать ответ с опорой на журнал и проверенное состояние.

### Остановка и голос

- Кнопка «Стоп» работает локально, без вызова LLM; запрещает новые действия, снимает ожидающие вызовы задачи и по возможности отменяет сетевой запрос. Поздний ответ отменённого запроса не запускает инструменты.
- Для явно адресованной голосовой команды остановки предусмотреть локальный обработчик после распознавания; не обещать работу без сети, пока не проверена доступность локального STT. Обычные слова в цитатах не считать командой.
- Различать «пауза» с возможностью продолжить и «отмена» задачи. Прерывание TTS само по себе не отменяет работу; дать отдельные понятные элементы управления.
- В следующей итерации достаточно push-to-talk и текста с возможностью дополнения во время работы; непрерывное прослушивание не становится обязательным.

## 16. Дополнительные приёмочные сценарии следующей итерации

1. Несколько задач и реплики диалога используют общую квоту без всплеска одновременных повторов; запросы распределены по времени.
2. 429 с серверным сроком блокирует соответствующую группу до срока; без подсказки применяются ограниченные повторы. Уже выполненный Android-клик не повторяется.
3. При суточном пределе агент сообщает причину, сохраняет задачу и не повторяет запрос каждую минуту.
4. Пользователь обсуждает варианты без запуска инструментов, затем даёт явное поручение в том же разговоре.
5. Агент задаёт вопрос → WAIT_USER → пользователь отвечает голосом или текстом → продолжается исходная задача.
6. Условие приходит во время запроса LLM: поздний ответ по старой версии не вызывает противоречащего условию действия.
7. Дополнение приходит между проверкой и передачей вызова: атомарная защита в ToolGateway не допускает исполнения устаревшего плана.
8. Несколько коротких дополнений сохраняются по порядку и могут объединиться в один запрос; ничего не теряется.
9. Стоп во время WAIT_QUOTA или запроса API предотвращает следующие действия; поздний ответ игнорируется для исполнения. Пауза и отмена различимы.
10. Во время выполнения доступен вопрос «почему ты так делаешь?»; ответ учитывает реальный журнал. При исчерпанной квоте UI честно показывает ожидание.

**Следующий шаг:** реализовать эти требования вместе с базовым ТЗ 0.7; затем собрать APK и проверить сценарии на устройстве. Этот документ фиксирует проектные решения, а не готовую реализацию.


## 17. Виджет рабочего стола — обязательное требование следующей итерации

**Согласовано 19 октября 2026:** виджет является быстрым входом в постоянный диалог из раздела 15. Это требование к будущей реализации, а не описание готовой функции.

- Виджет привязан к сохранённому conversation_id и показывает связанную текущую задачу. Нажатие не создаёт новый разговор или копию задачи. После перезапуска связь восстанавливается из локального хранилища.
- Компактное содержимое: последняя реплика или ожидающий вопрос агента, краткое состояние задачи и доступные действия. В WAIT_USER приоритет отображения у вопроса, на который нужен ответ владельца.
- Различать выполнение, ожидание ответа, ожидание API-квоты с доступным временем повтора, паузу, завершение и ошибку. Не выдавать устаревший статус за текущий; после восстановления обновлять его из контроллера.
- Управление: «Микрофон», «Открыть диалог», «Пауза/Продолжить» по текущему состоянию; во время работы отдельно доступен «Стоп». Пауза и отмена имеют разный эффект, как в разделе 15. Стоп обрабатывается локально без LLM.
- По нажатию открывается компактный экран текущего диалога с текстовым вводом и push-to-talk, историей и состоянием задачи. Желательно лёгкое оформление поверх рабочего стола; точный способ Activity/dialog выбрать при реализации с учётом ограничений Android. Отдельное разрешение на произвольные наложения не считать обязательным для базового виджета.
- Кнопка микрофона открывает разрешённый платформой экран захвата речи; не обещать непрерывную запись непосредственно внутри AppWidget. Закрытие экрана диалога не отменяет задачу и не стирает историю; исполнение продолжает существующий сервис в пределах разрешений Android.
- Виджет и основной экран используют единые ConversationStore/TaskStore и общий контроллер, API-очередь и правила актуальности плана. Обновление виджета само по себе не вызывает LLM.
- Не показывать ключи или другие секреты; дать настройку скрывать текст реплик и оставлять только статус. Обновлять по событиям состояния, не полагаться на частый фоновый опрос.

**Приёмка:** добавить виджет → открыть существующий диалог → дать задачу → закрыть экран → увидеть статус → получить уточнение в виджете → ответить голосом/текстом в том же диалоге → добавить условие во время работы → проверить паузу, продолжение и локальный Стоп → перезапустить приложение и проверить сохранность связи. На целевой прошивке отдельно проверить размещение, обновления и открытие микрофона; до испытаний не утверждать совместимость.

Время продолжения показывать как оценку при неизвестной доступности сервера; не обещать точный запуск. Не озвучивать каждое нажатие и не дублировать одно событие из чата, виджета и уведомления.

**Порядок реализации:** сначала корректное принятие дополнений во время работы и защита версии задачи; затем синхронизация поверхностей и виджет на том же контроллере; затем настройка краткой озвучиваемой обратной связи. Общий лимит API действует и для ответов в разговоре.

**Приёмка:** во время задачи спросить «Почему по датам?» — получить объяснение без ненужной остановки; добавить «Лучше по папкам проектов» — старый план не исполняется дальше в противоречащей части; ответить на один вопрос из виджета и затем открыть чат — вопрос уже закрыт; повторная доставка ответа не запускает второй шаг; статус WAIT_QUOTA одинаков во всех входах; одна смена состояния озвучивается один раз; принятие реплики не выдаётся за её обработку моделью.


## 19. Терминальный стиль и удобство интерфейса — согласовано 19.10.2026

Основание: владелец показал экран работающей версии 0.7 и подтвердил направление «старые системы, зелёные буквы». Это требование к доработке существующего интерфейса; новый дизайн пока не реализован.

- Почти чёрный фон, мягкий зелёный основной акцент, тонкие рамки и спокойная визуальная иерархия. Сохранять достаточный контраст, читаемость и масштабирование шрифта. Без мерцания, scanlines, сильного свечения и обязательных декоративных анимаций.
- Моноширинный шрифт для коротких статусов и команд; удобный для чтения обычный шрифт для длинных сообщений. Элементы управления должны оставаться узнаваемыми и удобными для касания; терминальная эстетика не требует ручного ввода команд.
- Главный экран — постоянный диалог. Внизу закреплён ввод текста, микрофон и отправка. Не загромождать верх крупными заголовками и постоянными пояснениями; модель и подключение показывать компактно.
- Во время исполнения — компактная карточка текущей задачи с понятным состоянием, паузой/продолжением и заметным Стоп. После завершения большую кнопку «Остановить» не показывать; переход к новому вводу остаётся доступным. Скрытие кнопки не меняет семантику локальной остановки активной задачи.
- Итог показывать один раз в диалоге. История задач и технические детали раскрываются отдельно, без повторения полного результата на том же экране. Настройки, память и журнал остаются в своих вкладках.
- Ожидание ответа, ожидание квоты и ошибку различать текстом/значком и при необходимости дополнительным цветовым акцентом; не полагаться только на цвет.
- Виджет и компактный диалог поддерживают тот же визуальный язык и единое состояние разделов 17–18.

Приёмка: на экране завершённой задачи нет большой неактуальной кнопки Стоп и повторного результата; при запуске задачи управление остановкой доступно; длинные русские реплики читаются без обрезания; клавиатура не закрывает ввод; увеличенный системный шрифт не ломает управление; все четыре вкладки и функции версии 0.7 сохранены. Сначала проверить макет на реальном размере экрана, затем реализовать и испытать на телефоне.
